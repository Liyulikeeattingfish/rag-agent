## 一、检索侧四档消融（47 条用例）

只改配置开关，用启动参数覆盖，不改一行代码：

| 档 | 关键词通道 | hybrid | rerank | rerankMinScore | Recall@3 | Recall@1 | MRR | nDCG@3 | 拒答率 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| 1 纯向量基线 | — | ✗ | ✗ | — | 95.24% | 85.71% | 0.9048 | 0.9172 | 60% |
| 2 混合召回 + RRF | pg_trgm | ✓ | ✗ | — | 97.62% | 88.10% | 0.9286 | 0.9410 | 60% |
| 3 + 精排（阈值占位 0.0） | pg_trgm | ✓ | ✓ | 0.0 | 100% | 97.62% | 0.9881 | 0.9912 | 60% |
| 4 + 精排拒答闸＝默认配置 | pg_trgm | ✓ | ✓ | 0.05 | 100% | 97.62% | 0.9881 | 0.9912 | **100%** |
| 2b 同档 2，换 BM25 | BM25 | ✓ | ✗ | — | 97.62% | **92.86%** | **0.9524** | **0.9586** | 20% |
| 4b 同档 4，换 BM25 | BM25 | ✓ | ✓ | 0.05 | 100% | 97.62% | 0.9881 | 0.9912 | 100% |

原始结果 JSON：`rerun/tier1-vector-only.json`、`tier2-hybrid-rrf.json`、`tier3-rerank-nothreshold.json`、
`tier4-default.json`、`tier2b-bm25-no-rerank.json`、`tier4b-bm25-full.json`。
每份 JSON 里都带 `config` 字段（生效配置回显），用来证明这一档**真的**跑在预期配置下。

复现：

~~~bash
mvn spring-boot:run -Dspring-boot.run.arguments="--rag.retrieval.hybrid-enabled=false --rag.retrieval.rerank-enabled=false"
curl http://localhost:8081/eval
~~~

### 四条结论

1. 混合召回把 Recall@3 95.24% → 97.62%、Recall@1 85.71% → 88.10%。
2. 精排把 Recall@1 88.10% → 97.62%、MRR 0.9286 → 0.9881。它解决的不是"能不能捞回来"，而是"排在第几"。
3. **拒答只能靠精排之后的阈值闸**：档 1~3 拒答率都是 60%，只有档 4 设了 `rerank-min-score=0.05` 才到 100%。
   原因是候选池从向量 top3 扩到 10 条后噪声更容易挤进前 3，而精排只排序、不拒答。
   **同一个结论在上一版 3 份文档的语料上出现过一次（75% → 50%），换语料后重演。**
4. **BM25 排名更准但单独用会让拒答更差**（档 2b 拒答率 20% < 档 2 的 60%）：
   它按"至少共享一个查询词"就返回，中文二元组下短查询几乎总能命中某个片段。
   加上精排闸后两者收敛（档 4 与 4b 完全相同）—— **关键词通道决定候选池，精排决定排序。**

## 二、生成侧评测（42 条正例）

`GET /eval-answer`：每条正例跑一遍完整回答链路（检索 + 拼 prompt + 生成），然后做两层检查。

| 指标 | 结果 | 口径 |
|---|:---:|---|
| 漏答率 | **0%** | 正例被检索层拒答的比例 |
| 引用覆盖率 | **97.62%** | 回答里含有落在实际资料范围内的 `[N]` 编号 |
| 忠实率 | **97.62%** | LLM-as-judge 判定"每句都有资料依据" |
| 越界引用 | 0 条 | 引用了不存在的编号 |
| 未判定 | 0 条 | 判定调用失败或返回不可解析（**不计入忠实，单独统计**） |

原始结果：`rerun/answer-eval.json`。

### 唯一一条失败值得单独说：它是"该答却拒答"，不是幻觉

- 问题：`重排模型会不会自己拒绝回答不相关的问题`（期望文档 `rerank.md`）
- 检索层**没有**拒答（hits 非空），资料里明确写着"重排只负责排序，不负责拒答"
- 模型仍然回了"资料中没有相关内容"，且没有标任何引用
- 判定结果：`faithful=false`，理由"参考资料[1]明确讨论了该问题，与回答断言矛盾"

结论：**忠实度指标单看会把"过度保守"也算成不忠实**，必须和引用覆盖率、漏答率一起看。
这三个指标衡量的本来就是三种不同的失败：没召回、没标依据、答了但没依据。

## 三、向量索引压测（2 万条 × 1024 维）

`GET /bench/vector-index?rows=20000&queries=200&topK=10&clusters=100`

| 方案 | 服务端耗时 | 索引构建 | 索引体积 | Recall@10 | 执行计划 |
|---|:---:|:---:|:---:|:---:|---|
| 精确扫描（无索引） | 41.2 ms | — | — | 100% | Seq Scan on bench_vectors |
| HNSW `ef_search=40` | **0.50 ms** | 11.4 s | 156 MB | 100% | Index Scan using bench_hnsw |
| HNSW `ef_search=100` | 0.62 ms | — | 156 MB | 100% | Index Scan using bench_hnsw |
| HNSW `ef_search=40`（字面量内联） | 0.60 ms | — | 156 MB | 100% | Index Scan using bench_hnsw |
| IVFFlat `lists=20, probes=4` | 3.23 ms | 0.8 s | 156 MB | 100% | Index Scan using bench_ivfflat |

原始结果：`rerun/vector-index-benchmark.json`（含每档的执行计划与服务端耗时）。

### 三个必须说清楚的点

1. **合成数据不能用均匀随机。** 1024 维里均匀随机的点几乎两两等距（维度灾难），
   ANN 召回会假性暴跌。第一版就是直接 `N(0, 0.3)` 加噪声，结果噪声范数 ≈ 0.3×√1024 ≈ 9.6，
   把模长为 1 的聚类中心彻底淹没，测出来 HNSW recall 只有 0.149、延迟和全表扫描一样。
   现在改成按 `σ/√D` 给噪声，并用「聚类中心 + 噪声」生成，才有邻域结构。
2. **HNSW 构建本身有随机性**（节点层数随机分配），多次运行召回在 98.5%~100% 之间浮动。
   这是算法固有性质，不是测量误差。
3. **客户端耗时在这组实验里没有区分度**：四组客户端 p50 都在 44~47 ms，而服务端差了 80 倍。
   我试过把查询向量内联进 SQL（绕开服务端预编译语句）来验证"通用计划导致索引失效"的猜想，
   **结果没有变化，所以那个猜想不成立**。最终以服务端 `EXPLAIN ANALYZE` 的 Execution Time 为准，
   客户端数字只作参考。这个现象没有查到底，就不编一个解释。

## 四、上一版（3 份文档语料）的结论

上一版在 3 份文档 5 个片段 / 20 条用例上测到：Recall@1 75% → 87.5% → 100%，
拒答率 75% → 50% → 100%。绝对数字因为语料太小没有外推意义，但**两个规律都站住了**：
加混合检索之后拒答率反而下降、必须补精排阈值闸。扩充语料到 12 份之后这两条再次复现。

## 五、复现时的坑（踩过，记下来）

- **重启脚本必须确认配置真的生效**：第一次跑四档时四个档位结果完全一样，
  原因是脚本用 `Get-NetTCPConnection` 找进程来 kill，它在某些 Windows 环境下会静默返回空，
  旧实例没被杀掉、`/eval` 打到的始终是旧实例。所以 `/eval` 会把生效配置一起返回 —— 用它自证。
- **`mvn compile` 之后要 `package`**：`java -jar` 跑的是打包后的 jar，只 compile 不 package 会测到旧代码。
- **批量导入后要 `ANALYZE`**：否则计划器拿不到真实行数统计，明明建了索引也可能选顺序扫描。
